<objective>
Extend the 2-second pipeline SSE payload so modules that exist on disk but were never loaded (VALIDATING / VALIDATED / APPROVED / FAILED) are visible to the pipeline graph, each carrying explicit `status`, `pending_approval`, and `build_stage` — where `build_stage` for an in-flight module is the LIVE build stage (scaffold / implement / tests / repair) taken from its BuildAuditLog.

Purpose: D-04 says "the graph is the notification" — but today `_build_pipeline_state()` sources modules exclusively from `loader.list_modules()`, which only knows *loaded* modules, so a VALIDATED module awaiting approval is invisible. D-13 additionally requires the build stages to render as a live progression on the graph; the stage names only exist inside `BuildAuditLog.attempts[].stage` (and `BuildSession.current_stage`, which is in-process and unreadable from the dashboard), so the SSE payload is the only place that link can be made. This is a backend gap, not a UI gap (RESEARCH Pattern 3). D-03 makes SSE the transport, and the Phase 6 rule is that the UI renders only from backend contracts — approval state and build stage must arrive in the payload, never be inferred client-side.
Output: a `_build_pending_approval_list()` helper plus a `_build_stage_index()` audit reader merged into the existing payload, the dashboard's `AUDIT_DIR` wiring, and unit tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MODULES_DIR on disk → SSE payload → browser | untrusted, LLM-generated manifest content is serialized to every connected UI client |
| AUDIT_DIR on disk → SSE payload → browser | build audit logs (job metadata, failure detail) become readable through an unauthenticated stream |
| unauthenticated SSE endpoint → module inventory | `/stream/pipeline-state` is in dashboard's `public_paths` (no API key required) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-11 | Information Disclosure | manifest fields streamed to unauthenticated SSE clients | mitigate | Emit only id/name/category/status/pending_approval/build_stage/state — never `api_key_instructions`, credential material, validation error details, or file paths |
| T-08-12 | Denial of Service | `ModuleManifest.discover` rglob every 2s over a large MODULES_DIR | accept | Scan is bounded by the module count in a single mounted volume (tens of dirs); `discover` already tolerates bad files. Revisit with a cache keyed on directory mtime only if a slow-cycle warning appears in logs |
| T-08-13 | Tampering | a crafted manifest.json crashing the stream for all clients | mitigate | Helper is fully wrapped in try/except returning `[]`; `discover` already skips unparseable manifests; unit test covers the malformed case |
| T-08-57 | Information Disclosure | BuildAuditLog content reaching the unauthenticated stream | mitigate | Only the single `stage` string of the latest attempt is extracted — never `job_id`, `logs`, `validation_report`, `failure_fingerprint`, `metadata`, or file paths. The full audit record stays behind the RBAC-gated `/admin/modules/{c}/{p}/audit` endpoint |
| T-08-58 | Denial of Service | parsing every `*_audit.json` every 2 seconds as the audit dir grows | mitigate | Scan is skipped entirely unless a module is in flight; then it stats (not parses) files, caps at the 50 newest, and re-parses only when the per-file mtime key changes. Malformed files are skipped, not retried |
</threat_model>
