<objective>
Deliver the chat half of D-02/D-17: approve and reject as `ModuleAdminTool` actions that resolve the caller's real identity and role from the chat session's API key, then call the same `shared/modules/approval.py` core the HTTP endpoints use.

Purpose: `08-PATTERNS.md` flags this explicitly as a wiring gap with no precedent to copy — every existing `ModuleAdminTool` strategy hardcodes `actor="chat_agent"`, and `orchestrator_service.py` still uses `org_id = "default"  # resolved from auth context in production`. Approving a module is a privileged security decision; it cannot be the one tool action that runs unauthenticated and unattributed.
Output: a session-identity contextvar, gRPC metadata resolution, two RBAC-guarded strategies, and unit tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| chat client → gRPC QueryAgent | an unauthenticated-by-default channel now carries a privileged action |
| LLM tool selection → approval core | a model decides to invoke a security-critical mutation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-40 | Elevation of Privilege | chat-initiated approve/reject | mitigate | `_require_admin_session()` fails closed on missing session and on any role lacking `WRITE_CONFIG` (D-17); the approval core itself still re-checks that the module is VALIDATED |
| T-08-41 | Elevation of Privilege | prompt injection making the agent call `approve_module` | mitigate | Authorization is bound to the SESSION key, not to the model's intent — an injected instruction executed under a viewer session cannot approve. Under an admin session the action is still recorded with that admin's identity, so it is attributable |
| T-08-42 | Repudiation | chat mutation attributed to "chat_agent" | mitigate | Strategies pass `actor=user.user_id` and an `ActorContext(channel="chat")` is active, so both the JSONL and the hash-chained SQLite audit rows carry the real principal |
| T-08-43 | Spoofing | forged `x-api-key` gRPC metadata | transfer | Keys are validated through `APIKeyStore.validate_key` (hashed lookup), the same path the HTTP middleware uses; transport confidentiality is the deployment's responsibility (insecure gRPC port today — pre-existing, unchanged by this plan) |
| T-08-44 | Information Disclosure | API key leaking into logs from the metadata reader | mitigate | `_get_session_user` never logs the key value; log only whether a session resolved and the resulting user_id |
</threat_model>
