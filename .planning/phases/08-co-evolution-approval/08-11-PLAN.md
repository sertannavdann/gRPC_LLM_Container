## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model-proposed tool call → rendered approval UI | the card's content is chosen by the LLM |
| chat user click → privileged mutation via /api/orchestrator | a security decision issued from the chat surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-45 | Spoofing | a model-crafted tool call impersonating an approval request for an arbitrary module | mitigate | The card is display-only: the actual mutation re-resolves the module server-side and requires an admin session (plan 08-10). The card always shows the concrete `module_id` and the fetched blueprint so the human sees what they are approving |
| T-08-46 | Elevation of Privilege | non-admin user clicking Approve Module | transfer | Enforced server-side by `_require_admin_session()`; the client deliberately has no role gate, and the 403 message surfaces in the card's failed state |
| T-08-47 | Tampering | model-supplied argument strings rendered in the card | mitigate | All values render as React text children through the existing `formatArguments` path; no `dangerouslySetInnerHTML` anywhere in the chat components |
| T-08-48 | Destruction of data | one-click terminal rejection from chat purging artifacts | mitigate | Two-click inline confirmation with the destructive copy, and the feedback textarea offers the reversible repair path first (D-09) |
</threat_model>
