# Phase 8 — UI Design Contract

> Visual and interaction contract for the module approval-gate UI: pipeline page pending-approval nodes, extended NodeDetailPanel review surface, chat approval cards, live build-stage progression, and the generic module output panel. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Autonomous mode note:** No user interaction was available for this session. Every value below is either (a) pre-populated from `08-CONTEXT.md` locked decisions D-01–D-19, (b) extracted directly from existing Phase 6 components (`StageNode.tsx`, `ModuleNode.tsx`, `ServiceNode.tsx`, `NodeDetailPanel.tsx`, `ActionCard.tsx`, `PipelineStageFlow.tsx`, `error-states.tsx`, `errors.ts`, `globals.css`, `tailwind.config.ts`), or (c) a discretionary assumption explicitly flagged `[ASSUMPTION]` with rationale. Open items are listed at the bottom under "Flags for Checker."

## Spacing Scale

Declared values (must be multiples of 4) — inherited from Phase 6, unchanged:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, badge internal padding, node micro-spacing |
| sm | 8px | Compact element spacing (node internal stacks, badge groups) |
| md | 16px | Default element spacing (panel section padding, card padding) |
| lg | 24px | Section padding (between NodeDetailPanel collapsible sections) |
| xl | 32px | Layout gaps (blueprint mini-graph margins) |
| 2xl | 48px | Major section breaks (not used inside panels; reserved for page-level layout) |
| 3xl | 64px | Page-level spacing (not used inside panels) |

Exceptions:
- **44px minimum touch target** for icon-only buttons in the chat `ApprovalActionCard` (approve/reject icon buttons at compact width) — matches WCAG 2.5.5 and the icon-button precedent already used in `NodeDetailPanel`'s close button, sized up from its current 32px (`p-1` + 16px icon) to 44px hit area for the destructive-adjacent reject control specifically. Regular approve/reject buttons in the full-width `NodeDetailPanel` footer use the existing `ActionCard.tsx` pattern (`px-3 py-2`, ~36px height) — no exception needed there since they're full-width text+icon buttons, not icon-only.
- React Flow node `min-w` values (130–170px) are a pre-existing Phase 6 exception for node card widths, not a new exception for this phase.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular) | 1.5 |
| Label | 12px (`text-xs`, uppercase, `tracking-wide`) | 600 (semibold) | 1.4 |
| Heading | 16px (`text-base`, panel/section titles) | 600 (semibold) | 1.3 |
| Display | 20px (`text-xl`, used only for the review panel's top-level module name in the expanded state) | 600 (semibold) | 1.2 |

Two weights declared: **400 regular** (body copy, code diff text, walkthrough prose, argument values) and **600 semibold** (labels, section headers, node titles, button text, badges).

**Documented exception (inherited from Phase 6, do not re-litigate):** React Flow node micro-labels and status badges use `text-[10px]`/`text-[11px]` (below the 12px floor) — this is an established Phase 6 pattern in `ModuleNode.tsx`, `ServiceNode.tsx`, `PipelineStageFlow.tsx` for space-constrained node chrome (attempt counters, category badges, latency figures). Phase 8's new node badges (pending-approval, stage labels) must reuse this exact `text-[10px]`/`text-[11px]` convention for consistency, not introduce a fifth type size.

**Legacy exception (inherited, out of scope):** `button.tsx` (shadcn Button primitive) uses `font-medium` (500) as its default weight. This predates this phase and is not to be changed; new Phase 8 components should use 400/600 per the table above, but reuse of the existing `<Button>` component is unaffected.

## Component Contracts

Prescriptive, per-surface specification for the seven key UI surfaces named in the task brief. All surfaces extend existing Phase 6 components — none are built from scratch.

### 1. Pipeline pending-approval node state (D-01, D-04)

Extends `ModuleNode.tsx`. A module reaching `VALIDATED` status is injected into the React Flow graph as a `module` node (not a new node type) with an added `pendingApproval: boolean` field on `ModuleNodeData`.

| State | Border | Fill | Badge |
|-------|--------|------|-------|
| `pendingApproval: true` | `border-amber-500/60` (2px, static — not the pulsing build-in-progress amber) | `bg-amber-500/10` | Top-right corner badge: 18px circle, `bg-orange-500` fill, white `Eye` icon (12px, lucide-react), Framer Motion `scale: [1, 1.08, 1]` loop (`duration: 1.8, repeat: Infinity, ease: 'easeInOut'`) — this pulse IS the notification per D-04, no toast/nav-badge needed |
| label suffix | append `"· Needs Review"` in `text-[10px] text-amber-400` under the module name, matching the existing `ModuleNode` badge-row layout |
| click target | entire node (existing `onClick` → `SELECT_NODE` pattern), opens `NodeDetailPanel` in review mode |

Copy: node subtitle reads exactly `"Needs Review"` (not "Pending" or "Awaiting Approval" — short enough for the 170px node width, matches Title Case convention of existing node labels).

### 2. Extended NodeDetailPanel review surface (D-06)

Extends `NodeDetailPanel.tsx`. When `node.type === 'module'` and `pendingApproval === true`, render five `@radix-ui/react-accordion` sections (type="multiple", all collapsed by default except section 1) below the existing Status section, using the panel's established `w-96`, `bg-zinc-900`, `border-zinc-700` shell — do not create a new panel component.

| # | Section | Default state | Icon (lucide-react) | Content source |
|---|---------|---------------|----------------------|-----------------|
| 1 | Blueprint | expanded | `LayoutTemplate` | See Surface 3 below |
| 2 | Code Diff | collapsed | `GitCompare` | `DraftManager.get_diff()` / equivalent draft diff endpoint — unified diff, monospace `text-[11px]`, `bg-zinc-950` block matching the existing `testResult.stdout` `<pre>` styling in `NodeDetailPanel` |
| 3 | Sandbox Validation Report | collapsed | `FlaskConical` | `manifest.validation_results` — reuse the existing pass/fail row pattern (`CheckCircle2`/`XCircle`, green/red) already used for the Test Runner section |
| 4 | Requested Credentials | collapsed | `KeyRound` | manifest credential requirements list — reuse the `Lock`/`Unlock` iconography from the existing Authentication section |
| 5 | Repair History | collapsed | `History` | `BuildAuditLog.attempts` — see Surface 4 (per-attempt timeline) below |

Accordion trigger row: `flex items-center justify-between px-3 py-2.5` matching the panel's existing `<section>` header rhythm (`text-xs font-medium text-zinc-400 uppercase tracking-wide`), with a `ChevronDown` (rotates 180° on expand via `transition-transform`) at the trailing edge.

Footer (sticky, below the accordion, `border-t border-zinc-700 px-4 py-3`): Approve/Reject button row per the Copywriting Contract above.

### 3. Progressive blueprint (D-05)

New component `BlueprintCard.tsx`, rendered inside accordion section 1.

**Collapsed (summary) state:** a "technical-drawing aesthetic" card — `border border-dashed border-zinc-600/50`, `bg-zinc-950/40`, monospace module name header, 4-row summary list (Adapter / Schema / Outputs / Credentials counts) each with a small dot + count, plus an "Expand blueprint" text button (`text-orange-400 text-xs`, `ChevronDown` icon). This reuses the exact dashed-border technical-drawing look already established by `StageNode.tsx` (`border-2 border-dashed`), giving the blueprint visual continuity with the pipeline's own stage nodes — this is the [ASSUMPTION] resolving Claude's Discretion item "blueprint card visual design": reuse StageNode's dashed aesthetic rather than inventing a new visual language, per the phase's own "one visual language, no bolted-on look" constraint (CONTEXT.md `<specifics>`).

**Expanded state:** on click, the card grows (Framer Motion `layout` animation, `AnimatePresence` height transition matching `TimeoutSkeleton`'s existing expand pattern) into a fixed-height (`h-64`) embedded `<ReactFlow>` mini-graph, `nodesDraggable={false}` `elementsSelectable={false}` (read-only, matching `PipelineStageFlow`'s existing read-only config). Mini-graph layout: horizontal left-to-right chain — `Adapter → Schema → Outputs → Credentials`, four nodes, each reusing the dashed-border stage-node visual at 50% scale (`min-w-[100px]`, `text-[11px]`), connected by static (non-animated) edges in `zinc-600`. [ASSUMPTION — layout algorithm]: fixed horizontal chain, not a force-directed layout, because the structure is always exactly this 4-step chain per D-05's own wording ("adapter → schema → outputs → required credentials as nodes") — no algorithm needed, positions are static `x` offsets like `STAGE_NODES` in `pipeline/page.tsx`.

### 4. Live build stage progression (D-13, D-14, D-15)

**Stage colors — reuse `PipelineStageFlow.tsx`'s `STAGE_COLORS` map verbatim, do not redefine:**

| Stage | Border hex | Bg | Text |
|-------|-----------|-----|------|
| scaffold | `#3b82f6` | `bg-blue-500/10` | `text-blue-400` |
| implement | `#8b5cf6` | `bg-purple-500/10` | `text-purple-400` |
| tests (validating) | `#f59e0b` | `bg-amber-500/10` | `text-amber-400` |
| repair | `#ef4444` | `bg-red-500/10` | `text-red-400` |

**Overall module-status states (superset of the 4 stages, covers the full lifecycle on the graph node):**

| Status | Visual rule |
|--------|-------------|
| `building` (scaffold/implement/tests in progress) | Node border animates through the current stage's color using the existing `PipelineStageNode` `animate={{ borderColor: [...] }}` pattern; status dot `bg-blue-400 animate-pulse` (reuse `STATUS_DOT.running`) |
| `validating` | Same as `building` but locked to the amber (tests) hue — this is `ModuleStatus.VALIDATING` per `manifest.py`, mapped 1:1 to the existing "tests" stage color, no new hue introduced |
| `pending-approval` | Static amber border (non-pulsing) + orange pulse badge — see Surface 1 above. Deliberately visually distinct from `validating`'s pulsing amber: static border + corner badge = "waiting on you"; pulsing border = "system is working" |
| `approved` | Green border (`#22c55e`), no animation, brief (600ms) `scale: [1, 1.05, 1]` spring pulse on transition-in (matches `ActionCard`'s `completed` entrance spring) |
| `rejected` | Red border (`#ef4444`), no animation, brief shake on transition-in (`x: [0, -10, 10, -10, 10, 0]`, reuse `ActionCard`'s exact `failed` shake keyframes) — node is visually marked rejected for one render cycle before the GC worker removes it from the next SSE payload (D-10); the node must not simply vanish silently (Phase 6 no-silent-fallback rule) |

**`pipelinePageMachine` (XState v5):** parallel regions `connection` (SSE `fromCallback` actor wrapping the existing `connectPipelineSSE()`), `reviewPanel` (`closed`/`open`), consistent with `financePageMachine`/`monitoringPageMachine` precedent. Framer Motion `AnimatePresence mode="wait"` governs section-level transitions inside the panel, matching the sitewide Phase 6 convention (`financePageMachine`'s exclusive-transition rule) — never overlap two build-state animations on the same node.

**Per-attempt timeline (D-15, accordion section 5):** vertical timeline, one row per `AttemptRecord` — `attempt_number` badge (circle, `bg-zinc-800`), `stage` label (colored per the stage table above), status icon (`CheckCircle2` green / `XCircle` red / `Loader2` animate-spin blue for in-flight), `failure_fingerprint.hash.slice(0,8)` shown as monospace `text-[10px] text-zinc-500` when present, connected by a `border-l border-zinc-700` vertical rule — this is a direct visual analog of GitHub's commit-timeline pattern, using only colors/components already declared in this spec.

### 5. Chat approval ActionCard extension (D-02)

New component `ApprovalActionCard.tsx`, extends `ActionCard.tsx` — same `rounded-lg border border-border bg-card p-4 space-y-3 max-w-md` shell, same `pending`/`executing`/`completed`/`failed` state machine and `AnimatePresence mode="wait"` transition pattern.

Additions over base `ActionCard`:
- Header icon: `Puzzle` (matches `ModuleNode`'s module icon) instead of the category icon map, since this card always represents a module, not an adapter tool call
- Below the arguments list: an inline, non-expandable mini blueprint — reuses `BlueprintCard`'s **collapsed** summary view only (4-row Adapter/Schema/Outputs/Credentials list). [ASSUMPTION — resolves Claude's Discretion "whether chat blueprint rendering reuses the mini-graph or a lighter variant"]: chat renders the **collapsed summary only**, never the expanded React Flow mini-graph — chat is a narrow, scroll-heavy surface where an embedded interactive graph would be disruptive; if the user wants the full interactive blueprint they follow the card's "Open in Pipeline" text link (`text-orange-400 text-xs`, opens `/pipeline` with the node pre-selected)
- Optional feedback input: a `<textarea>` (`text-sm`, `bg-zinc-950 border border-zinc-700 rounded-md p-2`, 2-row default, placeholder `"Optional: describe what to change…"`) appears between the arguments and the approve/reject buttons whenever `status === 'pending'`. Non-empty feedback + Reject → sends the D-09 repair-cycle copy ("sent back for one repair attempt…"); empty feedback + Reject → sends the terminal-rejection copy
- Approve/Reject buttons: identical styling to base `ActionCard` (`bg-green-500`/`bg-red-500`), labels changed to **"Approve Module"** / **"Reject Module"** per the Copywriting Contract

### 6. Auto-generated module panel (D-07)

New component, generic renderer keyed off `AdapterRunResult.data_points` and `AdapterRunResult.artifacts` — not a per-surface spec since it's explicitly generic (D-07: "modules do not hand-build UI"). Contract:

- Container: `rounded-lg border border-border bg-card p-4` (same shell as `ActionCard`/blueprint card — one card language across the app)
- `data_points`: rendered as a simple two-column key/value list (`text-sm`, label `text-muted-foreground`, value `text-foreground`) — same row pattern already used in `NodeDetailPanel`'s Status section (`flex items-center justify-between text-sm`)
- `artifacts` of chart type: rendered via Recharts, reusing the existing `ResponsiveContainer` + `initialDimension` SSR-safe pattern from `finance` page charts — chart type (line/bar/pie) inferred from the artifact's declared type field, not guessed from data shape [ASSUMPTION, resolves Claude's Discretion "chart-type inference"]: trust the artifact's own type metadata (already part of the `Artifact` model per `output_contract.py`) rather than building shape-sniffing heuristics
- Empty (`data_points` and `artifacts` both empty): reuse `EmptyState` component verbatim — heading `"No data yet"`, body `"This module hasn't returned any data. Run it from the pipeline or ask the assistant to use it."`

### 7. LLM walkthrough display (D-08)

Rendered as a distinct, visually marked block **above** accordion section 1 (not inside an accordion — it's meant to be read first, per "instructional review" framing in CONTEXT.md) inside the extended `NodeDetailPanel`.

- Container: `rounded-lg border border-violet-500/30 bg-violet-500/5 p-3` — [ASSUMPTION]: violet is used here deliberately as a "this is AI-generated explanatory text" marker, distinct from the amber (caution)/orange (accent)/green/red (status) semantic set already spoken for — violet-500 is otherwise unused for status semantics in this spec, avoiding collision, and is already precedented in the codebase for "AI/generated" contexts (`Sparkles`-adjacent gaming/calendar widget usage of violet/purple for non-human-generated content)
- Header row: `Sparkles` icon (12px, `text-violet-400`) + label `"How this module works"` (`text-xs font-semibold text-violet-300 uppercase tracking-wide`)
- Body: `text-sm text-zinc-300`, plain prose (reuse `react-markdown` + `remark-gfm`, already a dependency, for consistent formatting with chat messages), max 3 short paragraphs per generation constraint (walkthrough is generated once at validation time and stored — no live regeneration UI needed this phase)
