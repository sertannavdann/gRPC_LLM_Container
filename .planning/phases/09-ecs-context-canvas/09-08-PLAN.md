<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staged proposal (LLM-authored) -> rendered DOM | Model-authored strings become visible UI text |
| optimistic approved add -> canvas | Local state briefly diverges from backend truth |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-03 | Denial of Service (UX) | Optimistic `add_module` flickering out on the next snapshot | mitigate | `createPendingConfirmations` grace registry (4s = 2x the SSE tick) plus the distinct `confirming` node treatment; unresolved ids are removed through the ECS choke point after the grace window, never left as ghosts |
| T-09-20 | Tampering | Proposal preview mutating live world state | mitigate | `preview.ts` is pure and grep-gated (no `world.add`/`world.remove`/`.mutate(` calls); the overlay is applied to node `data`, and `previewViews` operates on a copy |
| T-09-06 | Information Disclosure | Credential names rendered into a node badge by a `set_credentials` delta line | mitigate | The delta line renders a COUNT (`credentials → n items`), never names; asserted by the preview unit test |
| T-09-21 | Spoofing (UX-level) | A proposal overlay mistaken for confirmed live state | mitigate | UI-SPEC's three-way distinguishability rule: violet dashed outline + `Sparkles` badge (proposed) vs amber solid + pulsing `Eye` (pending approval) vs zinc dashed + spinning `Loader2` (confirming); live state underneath is annotated, never replaced |
</threat_model>
