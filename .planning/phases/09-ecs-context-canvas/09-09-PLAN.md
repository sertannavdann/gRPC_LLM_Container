<objective>
Close the LLM write path end-to-end in the UI: ops arrive, stage as a proposal, render in the
detail panel, and get approved (applied through mediation) or rejected (rewound, with feedback).

Purpose: ROADMAP Done Criterion — "LLM proposal → preview → approve/reject flow works end-to-end;
rejection rewinds cleanly; approved ops appear in the next delta." 09-RESEARCH.md Open Question 2
resolves to "extend, don't rebuild": reuse `pipelinePageMachine`'s existing `reviewPanel` region
rather than introducing a fourth parallel region.

SCOPE DECISION (Claude's Discretion, recorded explicitly): no source artifact specifies a
transport for getting LLM-authored ops from the orchestrator into the browser. ROADMAP deliverables
name the mediation layer, not a chat/tool transport, and 09-RESEARCH.md states staged proposals stay
browser-only until approved. This plan therefore builds `submitCanvasOps()` as the single documented
ingress seam (callable from a future orchestrator-driven chat/ActionCard handler, and exposed on
`window.__nexusCanvas` in non-production builds so the flow is exercisable and testable today). An
orchestrator tool that emits canvas ops is NOT built in this phase and must be surfaced as a
follow-up, not silently assumed.

Output: ingress seam, machine branch, panel section, rewind toast, and page wiring.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM/console-authored ops -> `submitCanvasOps` | Fully untrusted structured input entering the browser mediation layer |
| human approval click -> live world mutation | The only path from staged to applied |
| `window.__nexusCanvas` global | A write handle exposed on the page object |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Elevation of Privilege | Ops submitted through `ingress.ts` targeting non-owned entity kinds | mitigate | `submitCanvasOps` adds no logic and cannot bypass anything — it forwards to `canvasMediation.propose`, where zod + `OWNERSHIP` run; the same checks re-run at sync and at approve |
| T-09-02 | Tampering | Proposal invalidated between opening the panel and clicking Approve | mitigate | `approveWithHistory` -> `mediation.approve` re-validates against the live world (point 3 of 3) and returns `ok:false`; the panel then renders "Proposal no longer valid" rather than applying a stale op (UI-SPEC Interaction Contract) |
| T-09-22 | Elevation of Privilege | `window.__nexusCanvas` reachable by injected/third-party script | mitigate | Registration requires `NODE_ENV !== 'production'` OR the explicit build-time flag `NEXT_PUBLIC_CANVAS_DEV_SEAM=1`, which the Dockerfile defaults to EMPTY (off) — only `docker-compose.yaml`'s local stack opts in, so a hardened/production image ships without the handle. Residual risk accepted for the local stack because the seam can only STAGE proposals: applying still requires a human clicking "Approve Change", and every staged op passes the full zod + `OWNERSHIP` validation |
| T-09-23 | Repudiation | An approved canvas op leaving no trace | accept | History's `EventLog` records every `approve` event with its ops for the page lifetime; durable audit for canvas ops is out of scope for this phase (Phase 7 audit trail covers backend mutations, and canvas ops do not reach the backend) |
| T-09-03 | Denial of Service (UX) | Optimistic add never confirmed by the backend | transfer | Handled by plan 08's pending-confirmation registry; this plan only calls `pending.mark(...)` |
</threat_model>
