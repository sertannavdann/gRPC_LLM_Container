# Phase 9 — UI Design Contract

> Visual and interaction contract for the ECS context-substrate canvas rebuild. This phase is
> primarily a **state-architecture refactor** — the pipeline canvas keeps its Phase 6/8 visual
> design unchanged. This contract exists to (a) lock "no visual regression" as a binding
> constraint and (b) specify the small set of genuinely new surfaces the ECS write path and
> history mechanism introduce. Generated by gsd-ui-researcher (autonomous mode — no user
> interaction available), verified by gsd-ui-checker.

**Autonomous mode note:** Every value below is either (a) pre-populated from `09-CONTEXT.md`
locked spike verdicts, (b) extracted directly from existing Phase 6/8 components
(`ModuleNode.tsx`, `NodeDetailPanel.tsx`, `StageNode.tsx`, `page.tsx`, `globals.css`), or (c) a
discretionary default explicitly flagged `[DEFAULT]` with rationale. No new visual language is
introduced — every new surface below extends an existing color/component/animation convention
already declared in `08-UI-SPEC.md`.

---

## Visual Regression Lock (READ FIRST)

**Binding constraint, not a discretionary section.** Phase 9 changes *how state flows* into the
canvas (SSE → ECS world → buffered React Flow patch), not *how the canvas looks*. The following
are explicitly locked as unchanged by this phase — any diff to these during implementation is a
regression, not a feature:

- `ModuleNode.tsx`'s five existing lifecycle renderings (`legacy`, `building`, `validating`,
  `pendingApproval`, `approved`, `rejected`) — colors, borders, badges, animations all unchanged.
- `ServiceNode.tsx`, `StageNode.tsx`, `ToolNode.tsx`, `AdapterNode.tsx` — untouched.
- `NodeDetailPanel.tsx`'s existing Status section, five-accordion module-review surface (D-06),
  and Approve/Reject Module footer — untouched; this phase only *adds* a new panel content
  variant alongside it (see Component Contracts §2), never replaces it.
- `page.tsx`'s toolbar layout, `ReactFlow` canvas chrome (`Background`, `Controls`, `MiniMap`),
  and node/edge color conventions (`stateEdgeColor`, `STAGE_COLORS`) — unchanged.
- The 60/30/10 color split, spacing scale, and typography contract from `08-UI-SPEC.md` —
  inherited verbatim (see below), not re-derived.

The only pixels this phase is allowed to add are: a proposal-preview overlay, a
pending-confirmation node treatment, undo/redo toolbar buttons, and a rewind toast. Everything
else in Component Contracts is either identical to or a minimal, convention-following extension
of an existing Phase 6/8 pattern.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | **"Approve Change"** — canvas-op proposal approval button in the NodeDetailPanel's new `canvasOpApproval` footer (green, same styling as Phase 8's "Approve Module"); paired destructive/secondary action **"Reject Change"** (red, same row) |
| Proposal badge label | `"Proposed"` (violet corner badge tooltip / accessible label) |
| Proposal delta line | `"{field} → {value}"` compact-DSL-style arrow notation, e.g. `status → disabled` (matches the verbalizer's own field-arrow convention for consistency between UI and LLM-facing text) |
| Pending-confirmation label | `"· Confirming…"` (appended under the module label, matches the existing `"· Needs Review"` suffix convention exactly) |
| Empty/invalidated-proposal state | Heading: **"Proposal no longer valid"** — Body: **"This entity changed before the proposal could be reviewed. Ask the assistant to try again."** |
| Error state (proposal panel) | **"Couldn't load the proposed change. [Retry], or check the pipeline for the latest state."** — reuses `DegradedBanner` amber pattern verbatim, same as every other panel-section error in `08-UI-SPEC.md` |
| Destructive confirmation — Reject Change | **No confirmation click required** (deliberate departure from Phase 8's double-click "Confirm Reject" pattern — see rationale below) — single click immediately rewinds and shows the rewind toast: `"Change rejected — canvas rewound to the previous state."` |
| Undo tooltip | `"Undo (Ctrl+Z)"` |
| Redo tooltip | `"Redo (Ctrl+Shift+Z)"` |
| Undo/redo disabled tooltip | Same tooltip text, button additionally shows `opacity-40 cursor-not-allowed` — no separate "nothing to undo" copy needed, the disabled visual state is sufficient (matches locked-adapter-card precedent) |

**Rationale for the no-confirmation departure:** Phase 8's "Reject Module" requires a
confirmation click because it is a terminal, unrecoverable action — it deletes generated code and
artifact history. Phase 9's "Reject Change" targets a single staged canvas op (e.g. `set_status`,
`move`) and is fully recoverable via the undo/redo snapshot ring this phase adds. The interaction
cost of a confirmation click is not justified once the action is undoable — this is a direct,
intentional consequence of the history mechanism (spike 008) existing at all, not a inconsistency
with Phase 8's pattern.

## Component Contracts

Five new surfaces, all extending existing Phase 6/8 components per the Visual Regression Lock —
none built from scratch as a new visual language.

### 1. Staged proposal preview overlay (canvas nodes)

Applies only to `ModuleNode` — the LOCKED ownership policy (spike 007) restricts LLM-authored ops
to `module`-kind entities, so no other node type ever renders this state. Rendered as an overlay
on top of the node's existing `resolveLifecycle()` rendering (from `ModuleNode.tsx`) — the live
state underneath is never hidden or replaced, only annotated, matching the LOCKED "preview is a
pure overlay on views" decision literally.

| Op kind | Visual treatment |
|---------|-------------------|
| `set_status` / `set_credentials` / `move` (existing node, field-level change) | Add a violet corner badge, **top-left** (16px circle, `bg-violet-500`, `Sparkles` icon 10px white) — positioned opposite the existing top-right `pendingApproval` orange badge so the two never collide on the same node. Add a dashed outline ring on top of the existing border via CSS `outline: 2px dashed rgba(139,92,246,0.4); outline-offset: 2px` (outline layer, not a border change — does not affect box layout, matches the "pure overlay" constraint). Append one line below the existing badge row: `text-[10px] text-violet-400 font-mono`, format `"{field} → {value}"` (e.g. `status → disabled`). |
| `add_module` (entity does not yet exist) | Render a **ghost node**: full node shell at 60% opacity, `border-2 border-dashed border-violet-500/50 bg-violet-500/5`, label prefixed `"(proposed) "`, no lifecycle badge (there is no live state to badge yet). Positioned using the same auto-layout logic `page.tsx` already applies to real module nodes (append to the module row). |
| `remove_module` (existing node, proposed for removal) | Existing live node rendering drops to 50% opacity and gains the same dashed violet outline as the field-level case, plus an appended label `text-[10px] text-violet-400` reading `"· Proposed Removal"`. |

### 2. Proposal review affordance — extends `reviewPanel` region + `NodeDetailPanel`

Per `09-RESEARCH.md` Open Question 2's recommendation ("extend, don't rebuild"): reuse the
existing `pipelinePageMachine` `reviewPanel` region (`closed`/`loading`/`open`/`approving`/
`rejecting`/`error`) verbatim — no fourth parallel region. The `open` substate now branches on
proposal kind:

- **`moduleApproval`** — existing Phase 8 five-accordion surface (D-06), completely unchanged.
- **`canvasOpApproval`** (NEW) — a single compact section rendered in the same `w-96` panel
  shell, below the existing Status section, **not** using the accordion pattern (one proposal =
  no need to collapse/expand):
  - Header row: `Sparkles` icon (violet, matches the walkthrough marker convention from D-08) +
    `"Proposed Change"` label (`text-xs font-semibold text-violet-300 uppercase tracking-wide`).
  - Body: one row per changed field, reusing the exact two-column key/value pattern already used
    in the panel's Status section and the generic module output panel (D-07) — label
    `text-muted-foreground`, changed value `text-violet-300 font-medium`.
  - Footer (sticky, identical shell to the module-approval footer): Approve/Reject button row per
    the Copywriting Contract (`"Approve Change"` / `"Reject Change"`), same green/red button
    styling as D-06's Approve/Reject Module — no new button treatment introduced.
- Trigger: clicking a `ModuleNode` with an active staged proposal opens the panel directly into
  `canvasOpApproval` via the existing `onNodeClick` → `SELECT_NODE` guard pattern — no extra click.
- Invalidated proposal (target changed before review): panel shows the Copywriting Contract's
  "Proposal no longer valid" empty state instead of the diff body.

### 3. Pending-confirmation state (optimistic module adds)

Applies immediately after a `canvasOpApproval` for `add_module` is approved, before the next SSE
snapshot confirms the entity server-side (the LOCKED grace-period requirement).

- Visual: deliberately a **third, distinct, muted** treatment — must not be confusable with either
  the violet proposal-preview ghost (§1) or the amber `pendingApproval` state (still-awaiting-
  human-review). `border-2 border-dashed border-zinc-500/50 bg-zinc-800/40`, node at 70% opacity,
  `Loader2` icon (12px, `text-zinc-400`, `animate-spin`) in place of any badge, label suffix
  `text-[10px] text-zinc-500` reading `"· Confirming…"`.
- Resolution: on the next SSE snapshot — if the entity is present, the buffered patch simply
  applies the real mirrored fields on the same render cycle (no extra animation needed, the muted
  treatment is replaced by whatever `resolveLifecycle()` now returns). If the entity is absent
  (optimistic add did not persist), the node fades out (`opacity: 1 → 0`, 200ms) rather than using
  the `rejected` shake — a fade signals silent backend divergence, distinct from an explicit
  user-driven rejection, while still satisfying Phase 6's "no silent fallback" rule (the node
  renders visibly for one cycle before removal, it does not simply vanish).
- Grace period: **[DEFAULT] 4 seconds** (2× the existing 2s SSE tick interval — gives one full
  missed-tick buffer before treating non-confirmation as failure). Adjustable at implementation
  time if the SSE interval changes; not a hard requirement from CONTEXT.md.

### 4. Undo/redo toolbar controls

- Placement: `page.tsx`'s existing toolbar right-hand icon-button cluster, inserted immediately
  **left of** the existing Refresh button — order left-to-right: Undo, Redo, Refresh (history
  controls before data controls).
- Styling: identical to the existing Refresh button — `p-1.5 rounded-md text-muted-foreground
  hover:text-foreground hover:bg-muted transition-colors`, icon `w-4 h-4`.
- Icons: `Undo2` / `Redo2` (lucide-react) — no new icon library.
- Disabled state: `opacity-40 cursor-not-allowed pointer-events-none` when the respective history
  is empty (undo: snapshot ring at its oldest entry; redo: event log exhausted) — reuses the exact
  disabled-opacity convention already established for locked adapter cards (Phase 6).
- Tooltips: native `title` attribute (matches Refresh button's existing pattern) — see
  Copywriting Contract.
- Keyboard shortcuts: `Ctrl+Z`/`Cmd+Z` (undo), `Ctrl+Shift+Z`/`Cmd+Shift+Z` (redo) — bound at the
  page level via a `keydown` listener matching `ChatInput.tsx`'s existing `handleKeyDown`
  convention. Guard: shortcuts are inert whenever an `<input>`/`<textarea>` currently has focus
  (prevents hijacking the browser's native undo inside the chat composer or a proposal-feedback
  textarea).

### 5. Rewind feedback toast

No toast library exists in `ui_service`, and Phase 8 established a "no modal/dialog, inline/
transient feedback only" precedent. This phase adds **one** new small hand-rolled component,
`RewindToast.tsx` — not a new dependency (consistent with `09-RESEARCH.md`'s Don't-Hand-Roll
guidance, which is scoped to ECS-internal serialization/dirty-tracking, not general UI feedback;
a single-purpose transient banner does not warrant installing `sonner` or similar).

- Trigger: fires only when a `"Reject Change"` action triggers an actual rewind (clear-then-
  restore, per the LOCKED history decision) — i.e., the world state differs before/after. A reject
  on an already-invalidated proposal (caught by 3-point re-validation) shows the panel's inline
  "Proposal no longer valid" message instead and does **not** trigger this toast.
- Visual: fixed position, `top-4 left-1/2 -translate-x-1/2`, `bg-zinc-800 border border-zinc-700
  rounded-md px-3 py-2 shadow-lg`, `RotateCcw` icon (14px, `text-zinc-400`) + `text-sm
  text-zinc-200`. Framer Motion `AnimatePresence`: `initial={{ opacity: 0, y: -8 }}` /
  `animate={{ opacity: 1, y: 0 }}` / `exit={{ opacity: 0, y: -8 }}` — matches the exclusive-
  transition convention already used sitewide (Phase 6 `AnimatePresence mode="wait"`).
- Auto-dismiss: 3000ms via `setTimeout`, no manual close button — matches the transient,
  non-blocking nature already established for other Framer-Motion-driven feedback in the app.
- Copy: exact text in Copywriting Contract table above.

## Interaction Contracts

Locked per `09-CONTEXT.md` and `09-RESEARCH.md` — these govern behavior, not pixels, but are
binding on the executor exactly like the visual contracts above.

| Interaction | Contract |
|-------------|----------|
| Drag | Unchanged from the buffered React Flow pattern (spike 001) — ECS position write-back happens on drag-stop only, never mid-drag. Per Pitfall 3, guard the write-back with an existence check (`if (n && entity)`) before writing, since the dragged entity may have been removed mid-drag by an intervening SSE sync (untested edge case per RESEARCH.md — verify manually before considering shipped). |
| Selection on entity removal | Clears **silently** — no toast, no visible transition. `selectedNodeId` becomes `null` and `NodeDetailPanel` closes with no additional feedback. This is the one deliberate, CONTEXT.md-scoped exception to Phase 6's "no silent fallback" rule — it applies to selection loss specifically (`clearSelectionIfMissing`), not to the visibly-animated node removal treatments (`rejected` shake, pending-confirmation fade) defined above, which remain visible per that same rule. |
| Hover | Unchanged — no new hover treatment introduced by this phase on any node type. |
| Rewind vs. plain reject | The rewind toast (§5) fires only when a rejection actually rewinds drifted state. A reject on an already-invalidated proposal shows the panel's inline empty-state message instead (no toast) — these are two different, non-overlapping feedback paths for two different situations. |
| Proposal re-validation | Per the LOCKED 3-point re-validation (proposal time, every SSE sync, approval time), a proposal can silently flip to "invalidated" between when a user opens the panel and when they click Approve. If this happens, the Approve button click must re-check validity and show the "Proposal no longer valid" message rather than attempting to apply a stale op — this is a UI-visible consequence of a state-architecture rule, not a new visual pattern. |

## Flags for Checker

1. **Violet is reused, not newly budgeted** — this phase's LLM-proposal treatment (badge, dashed
   outline, delta text, panel header) reuses Phase 8's existing violet "AI-generated content"
   reservation rather than introducing a new hue. If the checker's color-budget dimension counts
   per-phase hue additions strictly, this should register as zero new hues, one new *usage* of an
   existing hue.
2. **Reject Change has no confirmation click**, departing from Phase 8's Reject Module double-
   click pattern — justified explicitly above (recoverability via undo/redo). Flagged in case the
   checker's copywriting dimension expects confirmation-by-default for all reject actions.
3. **Pending-confirmation grace period (4s) is a `[DEFAULT]`**, not a CONTEXT.md-locked number —
   CONTEXT.md specifies the grace-period *mechanism* is required but not its duration. Planner/
   executor may adjust if the actual SSE interval differs from the assumed 2s.
4. **Three visually distinct "waiting" states now coexist** on `ModuleNode` (amber `pending
   Approval`, violet proposal-preview, muted-zinc pending-confirmation) — each was deliberately
   given a different hue/stroke-style pairing specifically to remain distinguishable from the
   other two on sight, extending Phase 8's own Flag 6 discipline (`pendingApproval` vs
   `validating` disambiguation) to a three-way distinction. Checker should verify no two of these
   three could be visually confused at a glance.
